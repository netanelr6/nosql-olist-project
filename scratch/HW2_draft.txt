שאלה 1: בחירת משפחת בסיסי נתונים והסבר
המשפחה שנבחרה: משפחת בסיסי נתונים מבוססי מסמכים (Document Store).
למה בחרנו במשפחה זו ואיך היא מתאימה למאגר? מאגר הנתונים של Olist מתעד שרשרת ערך של מסחר אלקטרוני (E-commerce) בעולם האמיתי. בעולם זה, ישות ההזמנה (Order) היא היררכית מטבעה: לקוח אחד מבצע הזמנה שמכילה מספר פריטים (Items), והיא משולמת באמצעות אמצעי תשלום אחד או יותר (Payments). במודל הרלציוני נאלצנו לפצל מידע זה ל-4 טבלאות שונות ולבצע פעולות JOIN יקרות כדי לשחזר את פרטי ההזמנה.
במודל הלא-רלציוני המבוסס על מסמכים (כמו מסמכי BSON ב-MongoDB), אנו יכולים לאגד (Embed) את כל פרטי ההזמנה, הפריטים, פרטי הלקוח והתשלומים לתוך מסמך אחד שלם. בצורה זו, שליפה של הזמנה אחת מביאה איתה את כל ההקשר הרלוונטי בפעולת קריאה בודדת ללא צורך ב-Joins, מה שמשפר משמעותית את הביצועים ומפשט את הלוגיקה האפליקטיבית.
מדוע המשפחות האחרות פחות מתאימות? פחות מתאימות ליישום הפרויקט בשל החסרונות הבאים:
1. מפתח-ערך (Key-Value): פשוט מדי עבור אופי הנתונים שלנו. מאגר Olist דורש שאילתות אנליטיות מורכבות (כמו ממוצעי דירוגים וחלוקה לקטגוריות). מודל מפתח-ערך לא תומך בבניית שאילתות סינון ואגרגציה מורכבות על שדות פנימיים ללא שליפת כל המידע ועיבודו בקוד האפליקציה.
2. עמודות (Column Family): מתאים לאנליטיקה רחבה על כמויות ענק של עמודות ספציפיות, אך הוא פחות אינטואיטיבי לייצוג היררכי וטבעי של תהליך רכישה קלאסי המכיל אובייקטים מקוננים (כמו מערך פריטים בתוך הזמנה).
3. גרפים (Graph DB): מתאים במיוחד למערכות קשרים סבוכות (כמו רשתות חברתיות). למרות שניתן להשתמש בו למערכות המלצה, הוא מסורבל ומורכב מדי לניהול השוטף של פעילויות הליבה של האתר (כמו יצירת הזמנות ועדכון מלאי).
בסיס הנתונים הלא-רלציוני הנבחר: MongoDB
קישור לאתר הרשמי: https://www.mongodb.com/

שאלה 2: שרטוט ERD של המודל הלא-רלציוני
תרשים ה-ERD הלא-רלציוני שעיצבנו עבור מאגר הנתונים מוצג בקובץ OlistNoSQLERD.svg (או OlistNoSQLERD.drawio לעריכה) שבתיקיית diagrams של הפרויקט. השרטוט מיישם תפיסה מודרנית של דה-נורמליזציה וקינון (Embedding) ומצמצם את המבנה המקורי מ-11 טבלאות רלציוניות ל-4 אוספים (Collections) מרכזיים בלבד:
1. אוסף Orders (אוסף הליבה): מזהה (_id): order_id. שדות: סטטוס ההזמנה, חותמות זמן של רכישה, אישור, מסירה משוערת ומסירה בפועל. אובייקטים מקוננים: לקוח (Customer), מערך פריטים (Items - מוצר, מוכר, מחיר, משלוח) ומערך תשלומים (Payments).
2. אוסף Products (קטלוג המוצרים): מזהה (_id): product_id. שדות: משקל, מידות, ומספר תמונות של המוצר. אובייקטים מקוננים: שם קטגוריה בפורטוגזית ושם קטגוריה מתורגם באנגלית (הטמעת התרגום חוסכת JOIN לטבלת תרגום חיצונית).
3. אוסף Sellers (אוסף המוכרים והשיווק): מזהה (_id): seller_id. שדות: עיר, מדינה ומיקוד של המוכר. אובייקטים מקוננים: onboarding_details המכיל את כל היסטוריית הגיוס של המוכר (ערוץ הגעה שיווקי origin, נציג מכירות שסגר won_date, SDR, SR ועוד) - בכך מוזגו טבלאות השיווק ישירות לתוך המוכר.
4. אוסף Reviews (ביקורות לקוחות): מזהה (_id): review_id. שדות: ציון הדירוג (1-5), כותרת, תוכן, ותאריכים. קשרים: מערך של מזהי הזמנות (Referenced order_ids) הקשורות לביקורת. בחרנו להשתמש בקישור (Reference) ולא בקינון (Embedding) מכיוון שביקורת בודדת יכולה להתייחס למספר הזמנות שונות שפוצלו מאותה רכישה, ושימוש בקישורים מונע שכפול מיותר של ביקורות זהות.

שאלה 3: טעינת הנתונים למערכת NoSQL

תהליך ה-ETL מבוצע במלואו על ידי קוד Python שכתבנו, והוא מורכב מ-3 שלבים עיקריים:

• שלב ה-SQL Ingestion: סקריפט src/load_to_sql.py יוצר את סכמת הטבלאות ב-PostgreSQL וטוען את הנתונים הגולמיים לטבלאות הרלציוניות.
• שלב ה-NoSQL Transformation: סקריפט src/load_to_mongo.py מבצע את פעולת הדה-נורמליזציה. הוא שולף את הנתונים מטבלאות ה-SQL השונות, מאגד אותם למבנים ההיררכיים (JSON/BSON) בהתאם ל-Schema Design שהגדרנו בשאלה 2, וטוען אותם לתוך MongoDB.
להלן בדיקת האימות שהרצנו מתוך קונטיינר ה-ETL באמצעות הסקריפט src/verify.py המאשרת כי כל הנתונים נטענו בהצלחה לקולקשנים ב-MongoDB:

שאלה 4: שליפת נתונים ותרגום שאילתות מ-SQL ל-MongoDB
שאילתה 1: מיהו נציג המכירות (SR) שהמוכרים שגייס קיבלו את ממוצע הדירוגים הגבוה ביותר?
מציאת 5 נציגי המכירות המובילים לפי ממוצע הדירוגים של ספקיהם (לנציגים עם מעל 10 ביקורות).
קוד ה-SQL המקורי מתרגיל 1:
SELECT     closed_deals.sr_id,    COUNT(DISTINCT reviews.review_id) AS total_reviews,    ROUND(AVG(reviews.review_score), 2) AS avg_review_scoreFROM     closed_dealsJOIN     order_items ON closed_deals.seller_id = order_items.seller_idJOIN     reviews ON order_items.order_id = reviews.order_idGROUP BY     closed_deals.sr_idHAVING     COUNT(DISTINCT reviews.review_id) > 10ORDER BY     avg_review_score DESCLIMIT 5;
הסבר היתכנות ב-NoSQL: השאילתה ישימה לחלוטין ב-MongoDB באמצעות שימוש ב-Aggregation Pipeline. היות שביקורות עשויות להתייחס למספר הזמנות, ואלו מכילות פריטים ממוכרים שונים שגויסו על ידי נציגי מכירות שונים, אנו משתמשים ב-$lookup כדי לחבר את האוספים (reviews -> orders -> sellers) ובשלב $group כפול כדי לספור ביקורות ייחודיות ולחשב ממוצע לכל נציג מכירות.
פקודת האגרגציה ב-MongoDB:
db.reviews.aggregate([  { "$unwind": "$order_id" },  {    "$lookup": {      "from": "orders",      "localField": "order_id",      "foreignField": "_id",      "as": "order_details"    }  },  { "$unwind": "$order_details" },  { "$unwind": "$order_details.items" },  {    "$lookup": {      "from": "sellers",      "localField": "order_details.items.seller_id",      "foreignField": "_id",      "as": "seller_details"    }  },  { "$unwind": "$seller_details" },  {    "$match": {      "seller_details.onboarding_details.sr_id": { "$exists": true, "$ne": null }    }  },  {    "$group": {      "_id": {        "sr_id": "$seller_details.onboarding_details.sr_id",        "review_id": "$_id"      },      "review_score": { "$first": "$review_score" }    }  },  {    "$group": {      "_id": "$_id.sr_id",      "total_reviews": { "$sum": 1 },      "avg_review_score": { "$avg": "$review_score" }    }  },  {    "$match": {      "total_reviews": { "$gt": 10 }    }  },  { "$sort": { "avg_review_score": -1 } },  { "$limit": 5 },  {    "$project": {      "_id": 0,      "sr_id": "$_id",      "total_reviews": 1,      "avg_review_score": { "$round": ["$avg_review_score", 2] }    }  }]);

שאילתה 2: באילו קטגוריות מוצרים יש את אחוז הביקורות השליליות (1-2) הגבוה ביותר?
זיהוי 5 קטגוריות המוצרים בעלות אחוז הביקורות השליליות הגבוה ביותר, והמחיר הממוצע של המוצרים בהן (לקטגוריות עם מעל 50 ביקורות).
קוד ה-SQL המקורי מתרגיל 1:
SELECT     products.product_category_name AS category_portuguese,    category_translation.product_category_name_english AS category_english,    COUNT(reviews.review_id) AS total_reviews,    SUM(CASE WHEN reviews.review_score IN (1, 2) THEN 1 ELSE 0 END) AS negative_reviews,    ROUND((SUM(CASE WHEN reviews.review_score IN (1, 2) THEN 1 ELSE 0 END) * 100.0) / COUNT(reviews.review_id), 2) AS negative_reviews_percentage,    ROUND(AVG(order_items.price), 2) AS avg_priceFROM     productsJOIN     category_translation ON products.product_category_name = category_translation.product_category_nameJOIN     order_items ON products.product_id = order_items.product_idJOIN     reviews ON order_items.order_id = reviews.order_idGROUP BY     products.product_category_name,     category_translation.product_category_name_englishHAVING     COUNT(reviews.review_id) > 50ORDER BY     negative_reviews_percentage DESCLIMIT 5;
הסבר היתכנות ב-NoSQL: השאילתה ישימה לחלוטין. בזכות ה-Schema Design שלנו, תרגום קטגוריית המוצר לאנגלית כבר pre-embedded בתוך מסמכי אוסף המוצרים (Products). לכן חסכנו JOIN חיצוני אחד. אנו משתמשים ב-$lookup כדי לחבר את המוצרים להזמנות ולביקורות ומחשבים את האחוז השלילי בעזרת תנאי $cond.
פקודת האגרגציה ב-MongoDB:
db.reviews.aggregate([  { "$unwind": "$order_id" },  {    "$lookup": {      "from": "orders",      "localField": "order_id",      "foreignField": "_id",      "as": "order_details"    }  },  { "$unwind": "$order_details" },  { "$unwind": "$order_details.items" },  {    "$lookup": {      "from": "products",      "localField": "order_details.items.product_id",      "foreignField": "_id",      "as": "product_details"    }  },  { "$unwind": "$product_details" },  {    "$group": {      "_id": {        "category_portuguese": "$product_details.product_category_name",        "category_english": "$product_details.product_category_name_english"      },      "total_reviews": { "$sum": 1 },      "negative_reviews": {        "$sum": {          "$cond": [            { "$in": ["$review_score", [1, 2]] },            1,            0          ]        }      },      "avg_price": { "$avg": "$order_details.items.price" }    }  },  {    "$match": {      "total_reviews": { "$gt": 50 }    }  },  {    "$project": {      "_id": 0,      "category_portuguese": "$_id.category_portuguese",      "category_english": "$_id.category_english",      "total_reviews": 1,      "negative_reviews": 1,      "negative_reviews_percentage": {        "$round": [          {            "$multiply": [              { "$divide": ["$negative_reviews", "$total_reviews"] },              100            ]          },          2        ]      },      "avg_price": { "$round": ["$avg_price", 2] }    }  },  { "$sort": { "negative_reviews_percentage": -1 } },  { "$limit": 5 }]);

שאילתה 3: החזר השקעה (ROI) של ערוצי שיווק שונים
מציאת סך ההכנסות ומספר המוכרים שגויסו מכל ערוץ שיווקי (Origin) של לידים (MQL).
קוד ה-SQL המקורי מתרגיל 1:
SELECT     marketing_qualified_leads.origin AS marketing_origin,    COUNT(DISTINCT closed_deals.seller_id) AS recruited_sellers,    ROUND(SUM(order_items.price), 2) AS total_revenue_generatedFROM     marketing_qualified_leadsJOIN     closed_deals ON marketing_qualified_leads.mql_id = closed_deals.mql_idJOIN     order_items ON closed_deals.seller_id = order_items.seller_idWHERE     marketing_qualified_leads.origin IS NOT NULLGROUP BY     marketing_qualified_leads.originORDER BY     total_revenue_generated DESC;
הסבר היתכנות ב-NoSQL: השאילתה ישימה. פרטי גיוס השיווק (onboarding_details) מקוננים ישירות בתוך אוסף המוכרים (Sellers). לכן אנו מתחילים מ-sellers, מסננים את המוכרים הרלוונטיים, מתחברים ל-orders שבהן המוכר מכר מוצרים ומסכמים את מחירי המוצרים לפי ערוץ השיווק.
פקודת האגרגציה ב-MongoDB:
db.sellers.aggregate([  {    "$match": {      "onboarding_details.origin": { "$exists": true, "$ne": null }    }  },  {    "$lookup": {      "from": "orders",      "localField": "_id",      "foreignField": "items.seller_id",      "as": "orders_list"    }  },  { "$unwind": "$orders_list" },  { "$unwind": "$orders_list.items" },  {    "$match": {      "$expr": { "$eq": ["$orders_list.items.seller_id", "$_id"] }    }  },  {    "$group": {      "_id": "$onboarding_details.origin",      "sellers_set": { "$addToSet": "$_id" },      "total_revenue_generated": { "$sum": "$orders_list.items.price" }    }  },  {    "$project": {      "_id": 0,      "marketing_origin": "$_id",      "recruited_sellers": { "$size": "$sellers_set" },      "total_revenue_generated": { "$round": ["$total_revenue_generated", 2] }    }  },  { "$sort": { "total_revenue_generated": -1 } }]);

שאילתה 4: השפעת איחור במסירת המשלוח על שביעות רצון הלקוח
ניתוח הפער בממוצע דירוגי הביקורות בין הזמנות שהגיעו בזמן או מוקדם לבין הזמנות שסופקו באיחור.
קוד ה-SQL המקורי מתרגיל 1:
SELECT     CASE         WHEN orders.order_delivered_customer_date > orders.order_estimated_delivery_date THEN 'Late Delivery'        ELSE 'On Time or Early'    END AS delivery_status,    COUNT(DISTINCT orders.order_id) AS total_orders,    ROUND(AVG(reviews.review_score), 2) AS avg_review_scoreFROM     ordersJOIN     reviews ON orders.order_id = reviews.order_idWHERE     orders.order_delivered_customer_date IS NOT NULL     AND orders.order_estimated_delivery_date IS NOT NULLGROUP BY     CASE         WHEN orders.order_delivered_customer_date > orders.order_estimated_delivery_date THEN 'Late Delivery'        ELSE 'On Time or Early'    END;
הסבר היתכנות ב-NoSQL: השאילתה ישימה. אנו מתחילים מאוסף הליבה Orders, מסננים הזמנות עם תאריכים תקינים, מתחברים לביקורות המתאימות ב-$lookup וממירים את תאריכי המסירה וההערכה למבנה תאריך בעזרת $dateFromString כדי להשוות ביניהם ולקבוע את הסטטוס.
פקודת האגרגציה ב-MongoDB:
db.orders.aggregate([  {    "$match": {      "delivered_customer_date": { "$exists": true, "$ne": null, "$ne": "" },      "estimated_delivery_date": { "$exists": true, "$ne": null, "$ne": "" }    }  },  {    "$lookup": {      "from": "reviews",      "localField": "_id",      "foreignField": "order_id",      "as": "reviews_details"    }  },  { "$unwind": "$reviews_details" },  {    "$addFields": {      "delivery_status": {        "$cond": [          {            "$gt": [              { "$dateFromString": { "dateString": "$delivered_customer_date" } },              { "$dateFromString": { "dateString": "$estimated_delivery_date" } }            ]          },          "Late Delivery",          "On Time or Early"        ]      }    }  },  {    "$group": {      "_id": "$delivery_status",      "orders_set": { "$addToSet": "$_id" },      "avg_review_score": { "$avg": "$reviews_details.review_score" }    }  },  {    "$project": {      "_id": 0,      "delivery_status": "$_id",      "total_orders": { "$size": "$orders_set" },      "avg_review_score": { "$round": ["$avg_review_score", 2] }    }  }]);
שאילתה 5: חסמי שילוח גיאוגרפיים (עלות משלוח חורגת מ-30% מערך המוצר)
איתור מדינות בברזיל שבהן עלות השילוח הממוצעת מהווה מעל 30% ממחיר המוצרים.
קוד ה-SQL המקורי מתרגיל 1:
SELECT     customers.customer_state,    COUNT(DISTINCT orders.order_id) AS total_orders,    ROUND(SUM(order_items.price), 2) AS total_revenue,    ROUND((SUM(order_items.freight_value) * 100.0) / SUM(order_items.price), 2) AS freight_to_price_percentageFROM     ordersJOIN     customers ON orders.customer_id = customers.customer_idJOIN     order_items ON orders.order_id = order_items.order_idGROUP BY     customers.customer_stateHAVING     (SUM(order_items.freight_value) / SUM(order_items.price)) > 0.30ORDER BY     freight_to_price_percentage DESC;
הסבר היתכנות ב-NoSQL (שיפור ביצועים דרמטי): בזכות תכנון הסכמה שלנו ב-NoSQL, השאילתה הזו רצה במהירות שיא עם אפס (0) JOINS! כל פרטי הלקוח (כולל המדינה שלו) וכן פריטי ההזמנה (כולל המחיר ודמי המשלוח) כבר pre-embedded בתוך מסמכי אוסף Orders. אנו רק פותחים את הפריטים באמצעות $unwind ומקבצים ישירות לפי customer.state ללא צורך בשום חיבור חיצוני.
פקודת האגרגציה ב-MongoDB:
db.orders.aggregate([  { "$unwind": "$items" },  {    "$group": {      "_id": "$customer.state",      "orders_set": { "$addToSet": "$_id" },      "total_revenue": { "$sum": "$items.price" },      "total_freight": { "$sum": "$items.freight_value" }    }  },  {    "$project": {      "_id": 0,      "customer_state": "$_id",      "total_orders": { "$size": "$orders_set" },      "total_revenue": { "$round": ["$total_revenue", 2] },      "freight_to_price_percentage": {        "$round": [          {            "$multiply": [              {                "$cond": [                  { "$eq": ["$total_revenue", 0] },                  0,                  { "$divide": ["$total_freight", "$total_revenue"] }                ]              },              100            ]          },          2        ]      }    }  },  {    "$match": {      "freight_to_price_percentage": { "$gt": 30.0 }    }  },  { "$sort": { "freight_to_price_percentage": -1 } }]);

שאלה 5: מאפייני Big Data (ששת ה-V-ים) במערכת Olist
1. Volume (נפח הנתונים): הנתונים ההיסטוריים כוללים כ-100,000 הזמנות, 100,000 לקוחות, 33,000 מוצרים ו-100,000 ביקורות. למרות שניתן להריץ אותם על מחשב יחיד, במערכות אמת של E-commerce הנפח גדל במהירות עם נתוני קליקים (Clickstream) ויומני שרתים. שימוש ב-NoSQL (MongoDB) מאפשר להתמודד עם נפחים אלו בקלות על ידי ביטול פעולות JOIN ועל ידי חלוקת עומסים אופקית (Sharding).
2. Velocity (קצב ייצור ועיבוד הנתונים): במערכת חיה של Olist מתבצעות עשרות הזמנות בשנייה, עם שיאים באירועים עונתיים (כמו בלאק פריידי). כתיבת נתונים במקביל ממספר שירותים דורשת בסיס נתונים מהיר. MongoDB מציע ביצועים גבוהים בכתיבה בזכות נעילה ברמת המסמך ומנוע WiredTiger, בניגוד לנעילות טבלאות ב-SQL.
3. Variety (מגוון סוגי הנתונים): מאגר Olist משלב נתונים מובנים (הזמנות, תשלומים), חצי-מובנים (קואורדינטות גיאוגרפיות ומבנים מקוננים) ולא-מובנים (טקסט חופשי של ביקורות לקוחות). הגמישות של MongoDB (Schema-less) מאפשרת לשמור את כל מגוון המידע הזה יחד ללא צורך בהגדרת סכמה נוקשה לכל שדה.
4. Veracity (אמינות ואיכות הנתונים): בנתוני Olist קיימים אתגרי אמינות כמו ערכים חסרים (למשל, תאריכי מסירה של הזמנות שבוטלו), כפילויות בפריטים ותרגום קטגוריות. ב-MongoDB שדות חסרים פשוט לא נשמרים במסמך (חיסכון במקום), וניתן להחיל חוקי אימות סכמה (Schema Validation) כדי להבטיח את איכות הנתונים המוזנים.
5. Value (הערך העסקי מהנתונים): הנתונים מניבים ערך עסקי עצום: ניתוח איכות ספקים (שאילתה 1), זיהוי מוצרים בעייתיים (שאילתה 2), חישוב ROI שיווקי (שאילתה 3), ייעול לוגיסטי (שאילתה 4) ואיתור חסמי משלוח (שאילתה 5). דה-נורמליזציה ב-MongoDB מאפשרת לשלוף את התובנות האלו במהירות.
6. Variability (תנודתיות ושינוי הסכמה): קצב הרכישות משתנה בקיצוניות לאורך השנה (עונתיות וחגים), והסכמה העסקית משתנה לאורך זמן (הוספת מאפייני מוצרים חדשים). הארכיטקטורה של MongoDB תומכת בשינויים דינמיים אלו ללא צורך בביצוע מיגרציות סכמה מורכבות המקובלות ב-SQL.
